# Achievements: departures from the RFC

**Status:** draft.

This document records where the achievements code departs from [`rfc/ACHIEVEMENTS.md`](https://github.com/grafana/pathfinder-rfcs/blob/f151ad2f26a9cdec5d926ab4b0be3f7b5aba943a/rfc/ACHIEVEMENTS.md) in `grafana/pathfinder-rfcs` at `f151ad2f26a9`. Most rows come from the per-tier criteria change ([#2463](https://github.com/grafana/grafana-pathfinder-app/pull/2463)). Code comments that cite an RFC section point here where the code no longer follows it.

An RFC amendment is intended for every row, at the end of the epic. Until then, this document and the `pkg/achievements` tests describe the behavior. A row marked **TODO** has no recorded rationale yet.

"PR intent" is the Intent section of #2463's description. The examples in rows 2, 3 and 6 come from the same product intent.

## Departures

| 1   | §2 (recognition is informational, with no points) and §3 non-goal 3 (points)                                     | A tier's goal is a number of points, and each rule is worth `worth` points, 1 when unset (`Rule.Worth` in `pkg/achievements/catalog.go`). Progress stores the points earned toward the lowest tier not held (`Progress.Points`, the required `points` field in `kinds/achievementprogress.cue`), and they reset when that tier is earned. There is no running total, score or ranking: the API reports points only as progress toward the next tier (`units` of `next`). | Points are new in this epic, introduced by Nick Ferraro (decider) as part of this PR's design. PR intent: a tier needs N points and lists several rules worth different amounts. For example, a dashboard with at least 3 panels is worth 1 point and one with features X, Y and Z is worth 2, so a tier's OR criteria are no longer all worth 1. The field name `points` is frozen once the kind ships (§6).                                                                       | Yes, at the end of the epic |
| 2   | §6.2: one optional counter of distinct units per definition, with thresholds; a new rule kind needs an amendment | Each tier carries its own requirement: a points `goal` and 1 to 16 `rules` (entity, action, `where`, `countBy` and `worth`). The definition-level `counter` is removed (`Tier` in `catalog.go`). The ledger of counted units stays achievement-wide, so a unit counts toward one tier only.                                                                                                                                                                              | PR intent: one criterion shared by every tier is too limiting, so each tier defines its own criteria and goal, and tiers need not be additive. For example, tier 1 wants 3 dashboards, tier 2 wants 2 alert rules created, and the final tier is a built journey, which an additive constraint cannot express.                                                                                                                                                                      | Yes, at the end of the epic |
| 3   | §6.3 step 4: every due tier not held is awarded, including one below a held tier                                 | Only the lowest tier not held accrues. An event scores the highest `worth` among that tier's matching rules, once. Reaching the goal awards exactly that tier, one tier per event, and surplus points are discarded (`evaluate` in `pkg/achievements/evaluate.go`).                                                                                                                                                                                                      | PR intent, decided semantics 1, 2, 3 and 5. Only one tier is earned at a time, and an item counts toward only one tier. Progress builds only for the lowest tier not held: letting tier 1 events earn half of tier 2 would be odd, and tiers check recall as well as expertise, which accruing every tier at once would hinder. An item scores its highest worth, once. Points do not carry over to the next tier.                                                                  | Yes, at the end of the epic |
| 4   | §5.4 and §6.3: the ledger keeps growing past the final tier; `complete` means the ledger is at the ceiling       | `complete` once every catalog tier is held, as well as when the ledger is full (`evaluate.go`). | 6   | §6.2: `at` strictly increases (and §2, tiers with strictly increasing thresholds)                                | Goals may repeat or come in any order (the "goals in any order" case, `tiersOf(5, 1, 5)`, in `catalog_test.go`). `/definitions` still serves each tier's own goal as `tiers[].at`, and decisions and `/my` still carry `next`.                                                                                                                                                                                                                                           | A goal is that tier's own requirement, counted from 0, not a cumulative threshold. | 7   | §6.2: occurrence counters stop at 50; §12 question 7                                                             | A tier with an occurrence-counted rule has a goal of at most 50, and an achievement's goals add up to at most 200 (`maxOccurrenceGoal` and `maxUnits` in `catalog.go`). | 8   | §6.2: every matcher must yield the counter's unit                                                                | Rules on the same entity and action must count the same unit only within one tier (`catalog.go`), so different tiers may count one pair by different units. As a result, an event posted again after its first post was saved, such as a client retry after a lost response, counts toward the next tier when that tier counts the pair by another unit.                                                                                                                 | Only the lowest tier not held scores an event, so only one tier's rules can match it at a time. **TODO:** no recorded decision on letting tiers count one pair by different units, given that retried events can then count twice.                                                                                                                                                                                                                                                  | Yes, at the end of the epic |
| 9   | §6.2 author rules and identity guard: inserted lower tiers are supported; a counter's unit never changes         | `achievements-check compat` refuses a tier inserted before a published one (`insertedBreaks`) and a lowered goal on a published tier (`loweredGoals` in `compat.go`). | 10  | §6.4: AchievementProgress carries the achievement id, the held set and `units`                                   | The kind adds a required `points` field (an integer from 0 to 199, default 0), and rows are stamped `schemaVersion` 2. | 15  | §6.3 step 5 and §5.5: create awards, then save progress with compare-and-swap                                    | Awards are still created before the save.
